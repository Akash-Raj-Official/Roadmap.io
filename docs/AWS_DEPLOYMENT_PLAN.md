# AWS Deployment & Containerization Architecture Plan

This document outlines the complete plan to deploy **Roadmap.io** (currently running on Vercel) onto self-hosted **AWS infrastructure** using **Terraform** for infrastructure provisioning and **Docker / Docker Compose** for containerization.

---

## 1. Required AWS Infrastructure Components

To run Roadmap.io reliably on AWS without unnecessary enterprise overhead, the following core components are required:

| Component | AWS Resource | Purpose | Recommended Specs / Settings |
| :--- | :--- | :--- | :--- |
| **Compute** | `aws_instance` | Hosts the Docker engine and runs application containers. | Current Terraform default is **t2.micro** (1 vCPU, 1 GiB RAM) with 2 GB swap configured by cloud-init. This is a low-cost test target; builds may be slower or memory-constrained compared with a larger instance. |
| **Storage** | `root_block_device` | OS, Docker runtime, base images, and application source code. | **20 GB gp3 SSD** with 3,000 IOPS / 125 MB/s throughput. |
| **Networking** | `aws_vpc`, `aws_subnets` | Public networking allowing outbound dependency pulling and inbound HTTP/SSH. | Default VPC or a dedicated Public Subnet with Internet Gateway. |
| **Security** | `aws_security_group` | Firewall controlling traffic into the EC2 instance. | • **Port 22 (SSH)**: Ingress restricted to admin IP.<br>• **Port 80 (HTTP)**: Ingress open to `0.0.0.0/0`.<br>• **Port 443 (HTTPS)**: Ingress open to `0.0.0.0/0` (when domain/SSL added).<br>• **All outbound**: Egress open to `0.0.0.0/0` (for npm, Docker hub, Turso DB). |
| **Access Keys** | `tls_private_key`, `aws_key_pair` | SSH key pair for administrative access to the instance. | 4096-bit RSA key pair automatically generated by Terraform. |
| **Operating System** | `data.aws_ami` | Operating system base image. | **Ubuntu 22.04 LTS (Jammy)** x86_64. |
| **Bootstrapping** | `user_data` (`templatefile`) | Automated cloud-init startup script. | Automatically installs Docker Engine, clones repository, injects production environment variables, and launches Docker Compose. |
| **Database** | External Turso DB (libSQL) | Stateless database connectivity. | Database remains external on **Turso** (matching Vercel production). Keeps the EC2 instance completely stateless and avoids EBS database corruption. |

## 2. Terraform Infrastructure Structure

The Terraform configuration is organized into modular, clean, single-responsibility files located under `infra/aws/`:

```
infra/aws/
├── versions.tf               # Terraform CLI & provider versions (aws, tls, local)
├── variables.tf              # Input variable declarations & validations
├── main.tf                   # Core resources: VPC lookup, Security Groups, Keys, EC2
├── user_data.sh.tftpl        # Cloud-init bash template for automated server provisioning
├── outputs.tf                # Output values: Public IP, SSH command, Web URL
└── terraform.tfvars.example  # Example values file (sensitive keys are kept out of git)
```

### Breakdown of Terraform Files

### 2.1 `versions.tf`
Specifies required Terraform version (>= 1.5.0) and required provider plugins:
- `hashicorp/aws` (~> 5.0)
- `hashicorp/tls` (~> 4.0)
- `hashicorp/local` (~> 2.5)

### 2.2 `variables.tf`
Configures inputs:
- `aws_region`: Target deployment region (default: `us-east-1`).
- `instance_type`: EC2 instance size (default: `t2.micro`).
- `repo_url` & `repo_branch`: Git repository and target branch for deployment.
- `ssh_ingress_cidr`: Allowed CIDR block for SSH access (e.g. `your.ip.address/32`).
- `auth_secret`: Auth.js JWT session secret (sensitive).
- `turso_database_url`: Turso database connection URL (sensitive).
- `turso_auth_token`: Turso authentication token (sensitive).

### 2.3 `main.tf`
Implements declarative infrastructure:
1. **SSH Key Pair**: Generates a 4096-bit RSA key (`tls_private_key`), registers the public key with AWS (`aws_key_pair`), and saves the private key locally as `roadmap-ai-key.pem` with `0600` permissions.
2. **Network Resolution**: Fetches default VPC and public subnets.
3. **Security Group**: Opens port 22 (SSH) and port 80 (HTTP).
4. **AMI Resolution**: Automatically retrieves the latest official Canonical Ubuntu 22.04 LTS AMI.
5. **EC2 Instance**: Launches the VM with the attached security group, key pair, and rendered `user_data`.

### 2.4 `user_data.sh.tftpl`
Automates instance bootstrapping:
1. Installs Docker CE, containerd, and `docker-compose-plugin` using official Docker apt repositories.
2. Clones the repository into `/opt/roadmap-ai`.
3. Creates the `/opt/roadmap-ai/.env.production` file containing `AUTH_SECRET`, `TURSO_DATABASE_URL`, and `TURSO_AUTH_TOKEN`.
4. Runs `docker compose up -d --build` to build the Next.js container and run it on port 80.

### 2.5 `outputs.tf`
Exposes access endpoints upon completion:
- `instance_public_ip`: Public IP of the deployed EC2 server.
- `app_url`: `http://<instance_public_ip>`
- `ssh_command`: Ready-to-run SSH command `ssh -i roadmap-ai-key.pem ubuntu@<ip>`

## 3. Containerization Strategy

### 3.1 What Containers are Required?

Depending on the deployment tier (Basic IP vs Production with Domain/SSL), the container architecture is structured as follows:

```
[ Incoming HTTP/HTTPS Traffic ]
               │
               ▼
   ┌───────────────────────┐
   │  Container 1 (app)    │  <-- Next.js 16 Standalone Server (Port 3000)
   │  Node.js 22 Slim      │
   └───────────┬───────────┘
               │
               ▼ (libSQL over HTTPS/WSS)
   ┌───────────────────────┐
   │    Turso Cloud DB     │  <-- Managed Serverless SQLite (Zero state on EC2)
   └───────────────────────┘
```

#### Container 1: `app` (Core Application Container) — **Required**
- **Role**: Runs the full-stack Next.js application (Server Actions, UI rendering, API routes).
- **Base Image**: `node:22-slim` (Debian-based).
  > **Why not Alpine?** The project uses `better-sqlite3` during dev/build utilities. Alpine uses `musl` libc which fails compiling native C++ bindings for node-gyp. Debian-slim (`glibc`) ensures native binary stability.
- **Multi-Stage Build Pipeline**:
  1. `deps`: Installs `python3`, `make`, `g++`, copies `package.json` and runs `npm ci`.
  2. `builder`: Copies dependencies and source code, sets `output: "standalone"` via `next.config.ts`, and executes `npm run build`.
  3. `runner`: Sets `NODE_ENV=production`, creates an unprivileged user `nextjs:nodejs` (UID 1001), copies only `.next/standalone`, `.next/static`, and `public`, reducing the image from ~1.2GB down to ~150MB.
- **Port**: Listens on `3000`, mapped to host port `80` (or `3000` behind reverse proxy).

#### Container 2: `caddy` or `nginx-certbot` (Reverse Proxy & TLS) — **Recommended for Production**
- **Role**: Automated SSL/TLS certificates (Let's Encrypt), HTTP-to-HTTPS redirect, domain handling, and gzip/brotli compression.
- **When needed**:
  - *Phase 2 (Current)*: Optional. Single container `app` binds directly to `80:3000` for public IP verification.
  - *Phase 2.1 (Domain Attached)*: Add a lightweight `caddy:alpine` container to `docker-compose.yml` to automatically handle HTTPS without manual certificate renewals.

#### Why No Database Container?
- The project is architected with **Turso (libSQL)** in production.
- Because database storage and replication are managed by Turso over the network, the EC2 instance remains **entirely stateless**.
- If the EC2 instance terminates, crashes, or is redeployed via Terraform, **no data is lost**.

## 4. Docker & Compose Specifications

### 4.1 Production Dockerfile (`Dockerfile`)
```dockerfile
FROM node:22-slim AS deps
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends \
  python3 make g++ \
  && rm -rf /var/lib/apt/lists/*
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-slim AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV AUTH_SECRET=build-placeholder
ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

FROM node:22-slim AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1
RUN groupadd --system --gid 1001 nodejs \
  && useradd --system --uid 1001 --gid nodejs nextjs

COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs
EXPOSE 3000
ENV PORT=3000
CMD ["node", "server.js"]
```

### 4.2 Docker Compose (`docker-compose.yml`)
```yaml
services:
  app:
    build: .
    ports:
      - "80:3000"
    env_file:
      - .env.production
    restart: unless-stopped
```

*(For domain with automatic SSL, Caddy can be added alongside `app` by mapping 80/443 to Caddy and routing internal network traffic to `app:3000`)*.

## 5. Execution & Deployment Workflow

### Step 1: Configure AWS CLI & Environment
Ensure AWS credentials are configured with suitable permissions:
```bash
aws sts get-caller-identity
```

### Step 2: Initialize & Review Terraform
```bash
cd infra/aws
terraform init
```

Set environment variables for secrets:
```bash
export TF_VAR_auth_secret="$(openssl rand -base64 32)"
export TF_VAR_turso_database_url="libsql://<your-turso-db>.turso.io"
export TF_VAR_turso_auth_token="<your-turso-token>"
# Optional: lock SSH to your IP
export TF_VAR_ssh_ingress_cidr="$(curl -s https://checkip.amazonaws.com)/32"
```

Preview infrastructure plan:
```bash
terraform plan -out=tfplan
```

### Step 3: Apply Infrastructure
```bash
terraform apply "tfplan"
rm -f tfplan
```

### Step 4: Verify Deployment
1. Wait ~2-3 minutes for cloud-init (`user_data.sh.tftpl`) to finish installing Docker and building the container.
2. View app in browser: `http://<instance_public_ip>`.
3. Check boot logs if troubleshooting:
   ```bash
   ssh -i roadmap-ai-key.pem ubuntu@<instance_public_ip>
   sudo cat /var/log/cloud-init-output.log
   sudo docker compose -f /opt/roadmap-ai/docker-compose.yml ps
   ```

### Step 5: Tear Down (Cost Optimization)
When testing is complete:
```bash
cd infra/aws
terraform destroy
```
